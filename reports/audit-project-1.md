## Findings

### [CRITICAL] Admin endpoint executes client-supplied SQL, and no route has access control
ID: SEC-05
File: app.py:47-57, app.py:59-78, controllers.py:128-134, controllers.py:167-186, controllers.py:229-235, controllers.py:237-252
Description: `POST /admin/query` (app.py:59-78) takes `dados.get("sql", "")` from the request body and passes it straight to `cursor.execute(query)`, with `db.commit()` on the non-SELECT branch. `POST /admin/reset-db` (app.py:47-57) empties all four tables with no check at all. No handler in the project contains an authentication or role check, and no guard middleware is registered in app.py. `login` (controllers.py:167-186) returns the user but issues neither token nor session, so there is nothing to verify: `GET /usuarios` lists every user, `GET /pedidos` lists every customer's orders, and `PUT /pedidos/<id>/status` lets any caller move any order to "aprovado" or "cancelado". The `usuarios.tipo` column exists with `admin`/`cliente` values (database.py:32, database.py:76-78) and is never read to decide anything.
Impact: Anyone who can reach port 5000 has full control of the database — `DROP TABLE`, full read of users and passwords, price and stock changes, destruction of all data in one call. This is not a sanitization gap that escaping fixes: arbitrary execution is the endpoint's designed behaviour. Combined with wide-open CORS (app.py:9) and no authentication, any web page the victim opens can issue these calls from their browser.
Recommendation: Remove `/admin/query` entirely (T-05) — there is no safe version of that endpoint. Put `/admin/reset-db` behind authentication with a role check, or drop it from the production app. Introduce deny-by-default authentication middleware (T-16), issue and verify a token at login (T-05), and scope `/pedidos` and `/usuarios` to the authenticated caller.

### [CRITICAL] SQL assembled by string concatenation throughout the data layer, including login
ID: SEC-03
File: models.py:28, models.py:47-50, models.py:57-61, models.py:68, models.py:92, models.py:109-111, models.py:126-129, models.py:140, models.py:148-151, models.py:155, models.py:157-161, models.py:163-166, models.py:174, models.py:188, models.py:192, models.py:220, models.py:224, models.py:279-281, models.py:289-297
Description: All 19 sites above build the statement text with `+` from request-supplied values. The paths demonstrably reachable with unconstrained text: `criar_produto` interpolates `nome`, `descricao` and `categoria` (models.py:47-50); `atualizar_produto` the same (models.py:57-61); `criar_usuario` interpolates `nome`, `email` and `senha` (models.py:126-129); `buscar_produtos` interpolates the search term and the category inside a `LIKE` (models.py:289-297); and `criar_pedido` interpolates `usuario_id` and, per item, `produto_id` and `quantidade` taken from the JSON body with no type validation (models.py:140, 148-151, 155-166). The worst case is login (models.py:109-111): `SELECT * FROM usuarios WHERE email = '" + email + "' AND senha = '" + senha + "'`. The `str(id)` interpolations on routes using the `<int:id>` converter (models.py:28, 68, 92, 174, 279) are not reachable with text, but follow the same pattern and are fixed alongside.
Impact: At login, sending `senha` as `' OR '1'='1` authenticates as the first user in the table — authentication bypass, not merely injection. On the other paths an attacker reads, alters or drops any table. There is also a correctness defect independent of security: a product whose name contains an apostrophe (`Camiseta O'Brien`) breaks the `INSERT` and returns 500, because the quote closes the literal.
Recommendation: Convert every call to parameterized `execute` with `?` placeholders (T-02), passing values in the parameter tuple. The correct pattern already exists in the project, at database.py:70-73 and database.py:80-83, where the seed uses `executemany` with `?`.

### [CRITICAL] Passwords stored in plain text and compared inside the SQL query
ID: SEC-04
File: database.py:31, database.py:75-83, models.py:105-120, models.py:122-131
Description: The `senha` column is plain `TEXT` with no treatment (database.py:31). `criar_usuario` writes the value exactly as received from the request body (models.py:126-129). The seed writes `admin123`, `123456` and `senha123` directly (database.py:75-83). Verification does not happen in code at all: login delegates the comparison to the database, in the `AND senha = '...'` clause (models.py:110), which is exact text equality. No hashing function exists anywhere in the project — not bcrypt, not scrypt, not argon2, not even a fast digest.
Impact: Any read of the `loja.db` file, any backup, and any of the injections above hands over the credentials in the clear. Because users reuse passwords, the leak propagates to accounts outside this system. Comparing inside the SQL is also what makes the SEC-03 authentication bypass possible, and it rules out any constant-time verification.
Recommendation: Apply a password KDF (T-03): write `generate_password_hash` / bcrypt on signup, look the user up by email only, and verify the hash in Python. Migrate the seed to write hashes. Existing stored passwords must be invalidated, not converted — they should already be considered compromised.

### [CRITICAL] User password returned in HTTP responses, and personal data printed to stdout
ID: SEC-02
File: models.py:79-87, models.py:95-103, controllers.py:128-134, controllers.py:136-144, controllers.py:161, controllers.py:179, controllers.py:182
Description: `get_todos_usuarios` (models.py:79-87) and `get_usuario_por_id` (models.py:95-103) build the response dictionary including `"senha": row["senha"]`. Those dictionaries go straight into the response bodies of `GET /usuarios` (controllers.py:132) and `GET /usuarios/<id>` (controllers.py:140), unfiltered. Login, by contrast, omits the field (models.py:114-119), which shows the omission was intended and forgotten in the other two serializers. Beyond the response, controllers.py:161, 179 and 182 print the user's email to stdout on signup, successful login and failed login.
Impact: `GET /usuarios` — an unauthenticated route per SEC-05 — returns the name, email and plain-text password of every registered user, the administrator included. That is a complete credential-database leak through a single GET request, with no exploitation required. Printing emails on failed logins builds, in the log, a list of valid addresses paired with access attempts.
Recommendation: Remove `senha` from the user serializers (T-04) and expose fields by explicit allowlist, never by copying the database row. Reduce logging to non-sensitive identifiers (`usuario_id`), never the email or the request body.

### [CRITICAL] Secret key hardcoded and internal configuration returned by the health check
ID: SEC-01
File: app.py:7, controllers.py:285-290
Description: `app.config["SECRET_KEY"] = "minha-chave-super-secreta-123"` is a literal in the version-controlled entry module (app.py:7). The same literal is repeated in the response body of `GET /health` (controllers.py:289), alongside `"ambiente": "producao"`, `"db_path": "loja.db"` and `"debug": True`.
Impact: The key that signs Flask sessions and tokens is public to anyone with the repository — and, because of the health check, to any anonymous client calling `GET /health`, without needing the code at all. Any value signed with it can be forged. The same endpoint confirms to an attacker that debug mode is on and reveals the database file path, which is exactly what they need before exploiting SEC-06.
Recommendation: Move the secret to an environment variable read by a config module, with no production default (T-01). Remove the `secret_key`, `debug`, `db_path` and `ambiente` fields from the health check response, which should report availability only. Rotate the key — it is already compromised by being in git history.

### [CRITICAL] Werkzeug interactive debugger exposed on all network interfaces
ID: SEC-06
File: app.py:8, app.py:9, app.py:88
Description: `app.config["DEBUG"] = True` (app.py:8) and `app.run(host="0.0.0.0", port=5000, debug=True)` (app.py:88) enable the Werkzeug interactive debugger and bind it to every interface, not just localhost. `CORS(app)` with no arguments (app.py:9) applies the most permissive policy possible — any origin — to every route, including `/admin/*` and `/login`. The `/health` response confirms `"ambiente": "producao"` next to `"debug": True`, i.e. the development configuration is the one intended to run in production.
Impact: The Werkzeug console allows executing arbitrary Python in the server process through the error page. On a non-local interface that is remote code execution on the host, not a tidiness issue — which is why this instance is raised from HIGH to CRITICAL. Unrestricted CORS, combined with the absence of authentication (SEC-05), lets any site call `/admin/reset-db` and `/admin/query` from the victim's browser.
Recommendation: Read the debug flag from the environment with a default of off, and never enable it together with `host="0.0.0.0"` (T-01); serve through WSGI (gunicorn/waitress) instead of `app.run`. Restrict CORS to an explicit origin list and apply it as configured middleware (T-16).

### [CRITICAL] God files: three files hold routing, configuration, SQL, business rules and serialization for all four entities
ID: LAY-01
File: models.py:1-314, controllers.py:1-292, app.py:1-88
Description: None of the three files has a single responsibility, and each one spans all four domains (produtos, usuarios, pedidos, relatórios).
`models.py` (314 lines) mixes: SQL queries (every function); the checkout business rule — stock validation and total calculation at models.py:133-169; a discount policy by revenue tier at models.py:256-262; and HTTP serialization, with dictionaries hand-built at models.py:12-21, 31-40, 79-86, 95-102, 114-119, 178-199, 211-231, 304-313.
`controllers.py` (292 lines) mixes: input validation (controllers.py:28-54, 72-90), domain rules (the valid-category list at controllers.py:52, the order state machine at controllers.py:242), notification side effects (controllers.py:208-210, 247-250), direct database access (controllers.py:264-290) and logging.
`app.py` (88 lines) mixes: application configuration (app.py:6-9), registration of all 17 routes (app.py:11-30), and handlers that run SQL directly, including four `DELETE` statements (app.py:47-78).
Impact: Any change to any entity touches the same files, which makes merge conflicts the norm and per-domain review impossible. No business rule can be tested without a real Flask and a real SQLite: the discount policy is reachable only through a database query, and product validation only through a `request` object. This is the structural cause of which the other layering findings are symptoms.
Recommendation: Decompose into the target layers (T-06): `models/` per entity holding persistence only, `controllers/` per entity holding HTTP only, `views/routes.py` for route registration, `services/` for rules that belong to no single entity, `config/` for configuration, and app.py reduced to a composition root.

### [HIGH] Business rules and side effects inside the HTTP handlers
ID: LAY-02
File: controllers.py:43-54, controllers.py:87-90, controllers.py:208-210, controllers.py:237-250
Description: `criar_produto` decides what a valid product is in the handler body: non-negative price and stock, a name between 2 and 200 characters, and, at controllers.py:52-54, the literal list of accepted categories. `atualizar_status_pedido` carries the order state machine in an inline list (controllers.py:242) and then decides what happens on each transition (controllers.py:247-250). Notification side effects are fired inline: controllers.py:208-210 emits "email", "SMS" and "push" via `print` after order creation, and controllers.py:248-250 emits approval and cancellation notices.
Impact: None of these rules is reachable by another caller. A scheduled job approving pending orders, a CLI command bulk-loading products, or a second endpoint would each have to copy the category list, the name-length bounds and the valid states — and would diverge on the first change, exactly as create and update product already have (QUA-01). The rule "on cancellation, return the stock" is written as `print` text at controllers.py:250 and never executed: the stock does not come back.
Recommendation: Extract the rules into the service/model layer (T-07), leaving the controller with request reading, orchestration and HTTP status selection. Move notifications behind an injected service called by the use case, and actually implement the stock return on cancellation.

### [HIGH] Business rules, aggregations and serialization inside the data layer
ID: LAY-03
File: models.py:133-169, models.py:235-273, models.py:12-21, models.py:178-199, models.py:211-231, models.py:304-313
Description: `models.criar_pedido` (models.py:133-169) is the entire checkout use case: it checks product existence, compares stock against the requested quantity, accumulates the total by multiplying price by quantity, writes the order and its items, and debits stock — and it returns business errors as `{"erro": "..."}`, a response format rather than a persistence result. `models.relatorio_vendas` (models.py:235-273) computes the discount policy by revenue tier (10% above 10000, 5% above 5000, 2% above 1000, models.py:256-262) and the average ticket — neither of which is a property of any entity. In parallel, every query function builds dictionaries already shaped for the HTTP response, including the nested `itens` list at models.py:178-199 and models.py:211-231.
Impact: This is the mirror image of LAY-02 and is missed more easily because the code sits in a file named `models.py`. The practical consequence: the discount policy cannot be tested or reused without a populated database, and the HTTP contract is coupled to the schema — renaming a column changes responses from endpoints that never asked for that field. Because serialization is duplicated in six places, any new response shape requires editing all of them.
Recommendation: Move checkout and reporting into `services/` (T-08), leaving the models with queries and their own entity's invariants. Return rows or domain objects rather than response dictionaries, and concentrate serialization in a dedicated layer (T-17).

### [HIGH] Global mutable connection, created and seeded inside the getter
ID: LAY-04
File: database.py:4-11, database.py:12-86, models.py:1 and every function in models.py, controllers.py:3
Description: `db_connection = None` is module-level mutable state (database.py:4), assigned on the first call to `get_db()` and shared by the whole process. The connection is opened with `check_same_thread=False` (database.py:10), a flag that disables sqlite3's thread check without anything taking its place. Besides returning the connection, `get_db()` also creates the four tables (database.py:14-53) and inserts sample data (database.py:56-84) — three responsibilities in a getter. Every function in `models.py` calls `get_db()` instead of receiving a connection, and `controllers.py:3` does the same.
Impact: No test can substitute a double for the database: any test of any rule needs the real SQLite, with tables created and seed data present. Flask in threaded mode serves concurrent requests on the same connection with no lock, so cursors and transactions from different requests interleave — this is the condition that turns DAT-02 into a cross-request defect. And creating the schema on first access means there is no migration path: a column change is not applied to existing databases, because `CREATE TABLE IF NOT EXISTS` does nothing.
Recommendation: Inject a per-request connection/session obtained through the framework's lifecycle (T-09), and move schema creation and seeding into an explicit script outside the read path. Receive the dependency as a parameter in the models instead of reaching for it through an import.

### [HIGH] Composition root and controllers accessing the database driver directly
ID: LAY-05
File: app.py:4, app.py:47-57, app.py:59-78, controllers.py:3, controllers.py:264-290
Description: `app.py`, whose role is to assemble the application, imports `get_db` (app.py:4) and defines two handlers that execute SQL: four `DELETE` statements in `reset_database` (app.py:51-54) and `cursor.execute(query)` in `executar_query` (app.py:69). `controllers.py` imports `get_db` (controllers.py:3) and, in `health_check`, runs four count queries straight on the cursor (controllers.py:266-274), bypassing the model layer. The intended direction is `app → views → controllers → models → database`; both imports jump from the outer edge to the base.
Impact: A file whose job is registering routes containing a `DELETE FROM usuarios` is the most direct evidence that the layers are decorative — the next developer concludes, correctly, that reaching the database from anywhere is acceptable. In practical terms there are now three places to look when a query misbehaves, and the health check counts benefit from no fix made in the models.
Recommendation: Extract the app.py handlers into their own controllers and models (T-06) — or remove them, in the case of `/admin/query` (SEC-05) — and move the health check counts into a model function. After the refactor, no module above `models/` should import `database`.

### [HIGH] A failure mid-checkout leaves partial state and leaks the transaction into the next request
ID: DAT-02
File: models.py:133-169, controllers.py:188-220, database.py:4-11
Description: `criar_pedido` writes the order (models.py:148-151) and then, per item, writes the item and debits stock (models.py:157-166), with a single `db.commit()` at the end (models.py:168). There is no `try/except` and no `rollback` anywhere in the function, and the controller's `except Exception` (controllers.py:218) only prints and answers 500 — also without a rollback. Because the connection is global and long-lived (database.py:4-11, see LAY-04), the implicit transaction opened by the first writes stays open on that connection after the failure.
Impact: An exception between the order insert and the last item — an `item` missing the `"quantidade"` key, which raises `KeyError`, or a SQL error caused by an apostrophe in a name — leaves the order recorded with some of its items and some of the stock debited. Worse: the orphaned writes stay pending on the shared connection and are committed by the first `db.commit()` of any later, unrelated request — a product creation, for instance. The effect is an inconsistent order appearing in the database in response to another user's action, which is precisely the kind of defect that cannot be reproduced during investigation.
Recommendation: Wrap the operation in an explicit transaction with a rollback on the error branch (T-10), and use a per-request connection (T-09) so an abandoned transaction cannot be committed by another request. Validate each item's structure before any write (T-15).

### [HIGH] No foreign keys in the schema, and deleting a product leaves orphaned records
ID: DAT-03
File: database.py:14-53, database.py:38-39, database.py:46-52, models.py:65-70, models.py:196, app.py:51-54
Description: The four tables declare relationships as plain integers: `pedidos.usuario_id` (database.py:39), `itens_pedido.pedido_id` and `itens_pedido.produto_id` (database.py:48-49) have no `REFERENCES`, no `ON DELETE` clause and no index. There is also no `PRAGMA foreign_keys = ON` — required per connection in SQLite, which does not enforce them by default. `deletar_produto` (models.py:65-70) runs a standalone `DELETE FROM produtos` without deleting or nulling the `itens_pedido` rows that reference it. The code documents the consequence itself: models.py:196 substitutes `"Desconhecido"` for the missing product name when building an order's items. The manual `DELETE` ordering in app.py:51-54 (itens, pedidos, produtos, usuarios) is further confirmation: the author knew the database would not handle it.
Impact: Deleting a product corrupts order history — the items remain with a `produto_id` pointing at nothing, and orders start listing "Desconhecido", losing the record of what was actually sold. Because reports and revenue are computed over that data, the accounting divergence is permanent and there is no recovery path. Orders can also be created for a nonexistent `usuario_id`, since neither the database nor the code verifies the user (controllers.py:198).
Recommendation: Declare the foreign keys with the intended delete policy and enable `PRAGMA foreign_keys = ON` when opening the connection (T-11). Replace the physical product delete with deactivation (`ativo = 0`) — the column already exists and is never used, see QUA-02 — preserving history, and verify that the user exists when creating an order.

### [HIGH] Product validation duplicated between create and update, with a divergence the update path lets through
ID: QUA-01
File: controllers.py:24-58, controllers.py:64-96, models.py:12-21, models.py:31-40, models.py:304-313, models.py:178-199, models.py:211-231
Description: `criar_produto` (controllers.py:28-54) and `atualizar_produto` (controllers.py:72-90) implement the same validation twice, and the copies have diverged: the update does not check the name length (missing relative to controllers.py:47-50) and does not validate the category against the accepted list (missing relative to controllers.py:52-54). Both write the same columns. The data layer has an analogous duplication: the product dictionary is rebuilt in full in three places (models.py:12-21, 31-40, 304-313), the user dictionary in two (models.py:79-86, 95-102), and the block enriching order items with the product name is identical, line for line, in `get_pedidos_usuario` (models.py:187-199) and `get_todos_pedidos` (models.py:219-231).
Impact: The divergence is not a future risk, it is a live failure: a product that cannot be created with a 1-character name or with `categoria: "qualquer-coisa"` can be put into that state by a `PUT` immediately after creation. The category rule, which exists to keep the catalogue filterable, is bypassable by anyone using the update endpoint. The six serialization copies guarantee that any new field will be forgotten in at least one of them — as already happened with `senha`, present in two user serializers and absent from the third (SEC-02).
Recommendation: Extract product validation into a single function called by both paths (T-19) and extract one serializer per entity, used by every query. Extract the item-enrichment block into a single function as well, resolved with a `JOIN` (see DAT-04).

### [MEDIUM] Configuration and paths hardcoded, with no config module
ID: LAY-06
File: app.py:7-8, app.py:88, app.py:36, database.py:5, controllers.py:285-288
Description: There is no configuration module and not a single environment read in the project. Present as literals in application files: the database path `"loja.db"` (database.py:5, repeated at controllers.py:287), the host `"0.0.0.0"` and port `5000` (app.py:88), the debug flag (app.py:8 and app.py:88), the version `"1.0.0"` (app.py:36 and, again, controllers.py:285) and the environment label `"producao"` (controllers.py:286). The secret among these values is handled separately as SEC-01, being a vulnerability rather than a maintainability issue.
Impact: Changing environment requires editing code — and, in the case of debug, editing the very file that also wires every route, so a configuration tweak risks the routing. Promoting the same artifact through dev, staging and production is impossible: each environment needs a different file. The version duplicated across two modules is already an opportunity for silent divergence between the index and the health check.
Recommendation: Create `config/settings.py` reading environment variables with development-safe defaults (T-01), and import the configuration in the layers that need the values instead of repeating literals.

### [MEDIUM] N+1 queries in the order listings, and a repeated per-item query at checkout
ID: DAT-04
File: models.py:171-201, models.py:203-233, models.py:133-169
Description: `get_pedidos_usuario` (models.py:171-201) fetches the orders in one query and then, inside the loop over the rows, opens `cursor2` to fetch each order's items (models.py:188) and, inside that nested loop, opens `cursor3` to fetch each product's name (models.py:192). `get_todos_pedidos` (models.py:203-233) repeats the identical structure. The cost is `1 + P + I` queries, where P is the number of orders returned and I the total item count across all of them — for 100 orders with 3 items each, 401 queries for a single response. `criar_pedido` has a simpler variant: it queries the product in the validation loop (models.py:140) and queries the same product again in the write loop (models.py:155), spending `2N` queries where `N` would do.
Impact: The response time of `GET /pedidos` grows linearly with the system's entire order history, not with the page size — and since there is no pagination (DAT-05), there is no bound. Combined with the single shared connection (LAY-04), one call to `/pedidos` on a database in real use serializes every other request behind it.
Recommendation: Replace the loops with one query joining `pedidos`, `itens_pedido` and `produtos`, grouping the items in memory (T-12). At checkout, load the needed products once before the loops and reuse the values already read.

### [MEDIUM] Listings and search without pagination
ID: DAT-05
File: models.py:4-22, models.py:72-87, models.py:203-233, models.py:285-314
Description: `get_todos_produtos` (`SELECT * FROM produtos`, models.py:7), `get_todos_usuarios` (models.py:75), `get_todos_pedidos` (models.py:206) and `buscar_produtos` (models.py:289-299) return every row, with no `LIMIT`, `OFFSET` or cursor, and the corresponding controllers accept no paging parameters (controllers.py:5-12, 128-134, 229-235, 111-126). All four tables grow with usage — none is a closed lookup table like a status list.
Impact: Every call loads the whole table into memory and serializes it to JSON; `GET /pedidos`, which already multiplies queries per order (DAT-04), degrades compoundingly. As the database grows, a single request can exhaust the process memory, and since there is no rate limit (API-04) and no authentication (SEC-05), that is triggerable by anyone, repeatedly.
Recommendation: Add validated `limit`/`offset` paging with a default and a hard maximum defined in configuration (T-13), and return the total alongside the page. Product search should follow the same contract.

### [MEDIUM] Exceptions caught in every handler and returned to the client verbatim
ID: API-02
File: controllers.py:10-12, controllers.py:21-22, controllers.py:60-62, controllers.py:95-96, controllers.py:108-109, controllers.py:125-126, controllers.py:133-134, controllers.py:143-144, controllers.py:164-165, controllers.py:185-186, controllers.py:218-220, controllers.py:226-227, controllers.py:234-235, controllers.py:254-255, controllers.py:261-262, controllers.py:291-292, app.py:77-78
Description: Seventeen handlers repeat the same `except Exception as e: return jsonify({"erro": str(e)}), 500` block, and no centralized error handler is registered on the application (app.py registers no `errorhandler`). The exception text goes into the response body intact. At app.py:78, on the arbitrary-SQL endpoint, it is the driver's own error that is returned.
Impact: Two failures at once. Information disclosure: a sqlite3 exception names tables and columns (`no such column: senha`), which hands the schema to an attacker and, on `/admin/query`, turns the error message into a database-mapping tool. And guaranteed duplication: seventeen copies of the same handling mean that distinguishing a validation error (400) from an internal failure (500) requires editing seventeen places — which is why type errors in input currently reach the client as 500 (API-03).
Recommendation: Register a centralized error handler (T-14) that logs the detail server-side and returns a generic, stable error body to the client, and delete the repeated `try/except` blocks from the handlers, keeping only targeted catches of expected exceptions.

### [MEDIUM] Input not validated at the boundary: types, formats and order items
ID: API-03
File: controllers.py:37-46, controllers.py:118-121, controllers.py:146-165, controllers.py:188-203, controllers.py:198
Description: Confirmed gaps: `criar_produto` compares `preco < 0` (controllers.py:43) without checking that `preco` is a number — a `"preco": "abc"` raises `TypeError` before any validation; `buscar_produtos` calls `float(preco_min)` with no handling (controllers.py:118-121), so `?preco_min=abc` raises `ValueError`; `criar_usuario` (controllers.py:146-165) validates neither email format, nor password length, nor uniqueness — and the schema has no `UNIQUE` on `usuarios.email` either (database.py:30), so two accounts can share an email and login resolves to the first; `criar_pedido` checks only that the item list is non-empty (controllers.py:200), without validating that each item has `produto_id` and `quantidade`, or that the quantity is a positive integer; and `if not usuario_id` (controllers.py:198) rejects the value `0` as missing and does not verify that the user exists.
Impact: Two distinct effects. Client errors are reported as server failures: malformed input produces 500 with exception text (API-02) instead of 400 with a useful message, and an item missing `"quantidade"` still drives the checkout into partial writes before failing (DAT-02). And there is a rule hole: a negative `quantidade` passes the stock check at models.py:144, lowers the order total and, at models.py:163-166, executes `estoque - (-N)`, increasing stock — it is possible to create negative-value orders that restock the catalogue.

### [MEDIUM] No middleware chain: no authentication, rate limit, body limit or central error handling
ID: API-04
File: app.py:6-30
Description: The composition root registers exactly one extension: `CORS(app)` (app.py:9), in its most permissive configuration. Nothing else is registered — no authentication middleware, no request limiting, no body size limit (`MAX_CONTENT_LENGTH` is not configured), no error handler, no request logging, no security headers. What should be cross-cutting is copy-pasted into the handlers: error handling appears seventeen times (API-02) and validation, where it exists, is rewritten per handler (QUA-01).
Impact: Each absence maps onto a concrete route in this application. With no rate limit on `POST /login`, which compares plain-text passwords (SEC-04), brute force is unlimited and undetectable. With no rate limit on `/admin/reset-db` and `/admin/query`, which also lack authentication (SEC-05), a simple loop takes the service down. With no body size limit, `POST /pedidos` accepts an arbitrarily long item list, and each item becomes queries (DAT-04). With no central error handler, fixing the exception leak means touching seventeen handlers.
Recommendation: Assemble the middleware chain in the composition root (T-16): deny-by-default authentication, rate limiting on the login and admin routes, `MAX_CONTENT_LENGTH`, a centralized error handler, structured request logging, and CORS restricted to explicit origins.

### [MEDIUM] Inconsistent response contract, and success returned for a write that did not happen
ID: API-05
File: controllers.py:237-252, controllers.py:20, controllers.py:29-54, controllers.py:142, controllers.py:58, controllers.py:93
Description: `atualizar_status_pedido` (controllers.py:237-252) validates the status and calls the model without checking that the order exists; `models.atualizar_status_pedido` (models.py:275-283) runs the `UPDATE` without inspecting `rowcount` and returns `True` unconditionally. A `PUT /pedidos/999999/status` affects zero rows and answers `200 {"sucesso": True, "mensagem": "Status atualizado"}`. On the envelope shape, error responses are inconsistent with each other: controllers.py:20 and controllers.py:183 include `"sucesso": False`, while controllers.py:29-54, 70, 73-90 and 142 return only `"erro"`; and `"mensagem"` appears in some success responses (controllers.py:58, 93, 107) and not others (controllers.py:9, 18, 124, 132).
Impact: The `200` on an update that did not occur is a correctness defect, not a style issue: the client records the status transition as applied and moves on — a dashboard shows the order as approved when nothing changed in the database, and no error is raised to investigate. This is what lifts the finding above LOW. The envelope inconsistency forces every client to handle two error shapes, and a client testing `sucesso === false` stops detecting most failures, because on most branches the field does not exist.
Recommendation: Check the resource exists and inspect `rowcount` before answering success, returning 404 when the write found no target (T-17). Standardize one envelope for success and one for errors, applied by a serialization layer and the central error handler rather than built in each handler.

The success path is therefore atomic. The real defect is the absence of a `rollback` on the failure path over a shared connection, reported as DAT-02.

This is not a code finding (there is no line to point at), but it is what makes Phase 3 risky: validating the refactor will depend on capturing the endpoint contract before the changes and replaying it afterwards, as the playbook prescribes.
- **No schema migrations.** Tables are created by `CREATE TABLE IF NOT EXISTS` inside `get_db()` (database.py:14-53), so schema changes do not apply to existing databases. Covered under LAY-04 from the coupling angle; recorded here as an operational fact.
- **The `loja.db` file does not exist in the directory at audit time** — the schema analysis was done against the DDL at database.py:14-53, not against a materialized database.
