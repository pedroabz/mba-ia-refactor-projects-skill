## Findings

### [CRITICAL] Production secrets hardcoded in source
ID: SEC-01
File: src/utils.js:1-7 (values at :2, :3, :4, :5) — consumed in src/AppManager.js:2,45 and src/app.js:3,12
Description: The `config` object declares credential literals that are version-controlled: `dbPass: "senha_super_secreta_prod_123"`, `paymentGatewayKey: "pk_live_1234567890abcdef"` (a `pk_live_` prefix, the shape of a production payment-gateway key), `dbUser: "admin_master"` and `smtpUser: "no-reply@fullcycle.com.br"`. Nothing in the project reads the environment — `grep -rn "process.env" src/` returns nothing — and no dotenv dependency is declared. Three of the four credentials (`dbUser`, `dbPass`, `smtpUser`) are referenced by no code at all: they are declared and dead, which changes the fix (they can be deleted rather than migrated) but does not make them safe — a committed production password is compromised whether or not it is read.
Impact: Anyone with read access to the repository — or to the git history, where the value survives being edited out — obtains the payment-gateway key and the database password. The gateway key is replayable against the external provider, and these credentials can only be rotated at the provider, not in this code. The absence of any environment read also makes a dev/production configuration split impossible.
Recommendation: T-01 — extract a `config/` layer that reads `process.env` and validates presence at boot (fail fast when a required variable is missing), remove the literals from source, delete the three dead keys, add `.env` to `.gitignore` and ship a valueless `.env.example`. Rotate the gateway key and the database password outside this codebase — both must be treated as leaked.

### [CRITICAL] Full card number and gateway key written to the log
ID: SEC-02
File: src/AppManager.js:45
Description: `console.log(`Processando cartão ${cc} na chave ${config.paymentGatewayKey}`)` interpolates the full PAN received in `req.body.card` together with the `pk_live_...` key into stdout on every checkout request. The value is neither truncated, masked nor redacted, and the route is public (see SEC-05). No sensitive data reaches a response body — this was verified: checkout returns only `{msg, enrollment_id}` (:60) and the financial report returns only `name` and amounts paid (:112-115), never `pass`. The exposure vector here is the log alone.
Impact: Cardholder data in clear text on stdout. In production stdout is typically collected by an agent and shipped to a third-party observability service, which spreads both the PAN and a production key outside the application perimeter and into a system never designed to store them — a direct PCI-DSS violation on top of OWASP A09. Anyone with log access holds the card and the gateway key together, on the same line.
Recommendation: T-04 — delete the line. If the payment attempt must be traceable, record only non-sensitive identifiers (enrollment id, last four digits, brand) through the structured logger of T-23, and never the gateway key. The PAN should not travel through the application at all once T-07 moves payment behind a service that talks to the real gateway.

### [CRITICAL] Hand-rolled password hash that collapses the password space, plaintext seed, and a known default password
ID: SEC-04
File: src/utils.js:17-23 (`badCrypto`) — called at src/AppManager.js:68; plaintext seed at src/AppManager.js:18
Description: `badCrypto` concatenates the first 2 characters of `base64(password)` ten thousand times and returns the first 10 characters of the result — that is, it always returns the same two characters repeated five times. The output depends only on the first 12 bits of the password; the 10,000-iteration loop builds a 20,000-character string that is discarded entirely and is not a KDF cost factor. Measured by running the function itself: `"senhaforte"`, `"senha123"` and `"sexo"` all produce `c2c2c2c2c2`; `"123456"`, `"123"` and `"1234567890abcdef"` all produce `MTMTMTMTMT`; 5,000 distinct passwords of the form `pw<N>` produce **1** distinct hash. There is no per-user salt. On top of that: the seed at :18 writes `'123'` in plaintext, bypassing `badCrypto` entirely; and :68 uses `badCrypto(p || "123456")`, so a checkout without the `pwd` field creates the account with a publicly known default password. No code anywhere in the project ever compares a password — there is no login endpoint and the `pass` column is never read.
Impact: The password space collapses to a few thousand possible outputs, so any stored hash is brute-forced over two characters in negligible time, and different passwords from different users collide. Because no verification exists anywhere, the problem is larger than weak hashing: the column is write-only and the application has no authentication at all (see SEC-05) — the credential is collected, weakened and stored without ever serving a purpose. Accounts created without `pwd` become accessible with `123456` the day a login is implemented.
Recommendation: T-03 — remove `badCrypto` and use a password KDF (bcrypt, scrypt via `node:crypto`, or argon2) with a per-user salt and a configurable cost; fix the seed to write through the KDF; make `pwd` required in the T-15 validation rather than defaulting it (the default is part of this finding, not only of API-03). Decide explicitly whether password capture belongs in checkout at all: with no authentication flow, not collecting the password is safer than storing it.

### [CRITICAL] No access control on any of the three routes, including a destructive one and an admin report
ID: SEC-05
File: src/AppManager.js:28 (POST /api/checkout), :80 (GET /api/admin/financial-report), :131 (DELETE /api/users/:id) — composition root at src/app.js:5-10
Description: No handler performs an identity or role check, and no guard middleware is registered: `app.js` registers only `express.json()` (:6). A sweep for authentication signals across `src/` finds nothing — no token, session, JWT, authorization header, role column or roles table. All three routes are anonymous: `DELETE /api/users/:id` permanently removes any user from a path id with no check whatsoever; `GET /api/admin/financial-report` sits under an `/admin` prefix with no role check and returns platform-wide revenue plus the name of every student enrolled in every course; `POST /api/checkout` accepts anyone's email and creates an enrollment and a payment in their name.
Impact: An anonymous caller wipes the user table with one `curl` (`DELETE /api/users/1`), reads the company's full revenue and named student list, and enrolls third parties without their involvement. The deletion is irreversible and, per DAT-03, leaves orphaned enrollments and payments behind. Because the failure is the absence of the mechanism rather than a check forgotten on one route, every route added in future is unprotected by default — the opposite of deny by default (OWASP A01).
Recommendation: T-05 plus T-16 — introduce authentication and role-authorization middleware registered in the composition root, deny by default, and require an administrative role on the financial report; `DELETE /api/users/:id` must require authentication and authorization (the user themselves or an administrator). Until an identity model exists, the delete route should not be exposed.

### [CRITICAL] God class: `AppManager` holds DDL, seeds, routing, SQL over five tables, the payment rule and serialization
ID: LAY-01
File: src/AppManager.js:1-141 (the whole class)
Description: A single 141-line file accumulates seven distinct responsibilities, each belonging to a different layer: schema/DDL creation (:12-16), seed loading (:18-21), HTTP route registration (:28, :80, :131), database connection construction (:7), raw SQL data access across all five tables (:37, :40, :50, :54, :57, :69, :83, :92, :104, :106, :133), the payment-approval business rule (:45-48), report aggregation (:86-122) and response serialization (:60, :90, :112-115). Its scope covers four unrelated domain entities (users, courses, enrollments, payments) plus the audit trail. The class name describes no responsibility, which is consistent with it not having one.
Impact: Every change to any entity, any rule and any route edits the same file, maximizing merge conflicts and regression blast radius: reshaping the report and swapping the payment gateway are edits to the same block of code. Nothing is testable in isolation — there is no way to exercise the payment-approval rule without booting Express and a SQLite database, because the rule lives inside a callback inside a handler. This is the separation-of-concerns violation that the rest of this report unpacks.
Recommendation: T-06 — decompose into the layers defined in `architecture-guidelines.md`: `config/` for configuration and the connection, `models/` (or repositories) for per-entity SQL, `controllers/` for per-use-case orchestration, `views/routes` for route registration, `middlewares/` for cross-cutting concerns, and `app.js` as composition root. DDL and seeds move to a separate database-initialization module, not into the request path.

### [CRITICAL] Checkout writes to four tables with no transactional boundary
ID: DAT-01
File: src/AppManager.js:43-64 (writes at :50 enrollments, :54 payments, :57 audit_logs) and :69 (users)
Description: One business operation — enroll and pay — issues up to four INSERTs across different tables with no `BEGIN`/`COMMIT` around them. The `sqlite3` driver autocommits per statement by default; `db.serialize()` (used only in `initDb`, :11, not in checkout) orders execution but opens no transaction. Each INSERT therefore commits on its own, and there are error returns between them: :51 responds 500 after the user row has already been created, :55 responds 500 after the enrollment has already committed. An aggravating ordering problem: payment "processing" happens at :45-48, **before** any write, so the charge is decided first and the records are written afterwards.
Impact: Concrete, persistent partial states. If the `payments` INSERT fails, a committed enrollment remains with no payment at all — the student has course access with no charge on record, and no later query can distinguish that from fraud. If the `enrollments` INSERT fails, a user is left created with no enrollment. Because payment is decided before the writes, a database failure produces a charge with no counterpart. None of these paths has a rollback or a compensating action, and the 500 response does not tell the client what was persisted.
Recommendation: T-10 — wrap the whole operation in an explicit transaction (`BEGIN IMMEDIATE` … `COMMIT`, with `ROLLBACK` on every error path), exposed as a unit of work that the checkout controller opens and closes exactly once. Reorder so that payment authorization happens alongside persistence rather than before it, and so that the audit trail does not participate in the business success decision.

### [HIGH] Payment-approval rule and implicit user creation inside the handler
ID: LAY-02
File: src/AppManager.js:45-48 (approval), :66-72 (user creation), :108-110 (revenue rule)
Description: The checkout handler decides payment approval with `let status = cc.startsWith("4") ? "PAID" : "DENIED"` — the entire payment policy is an inspection of the card's first digit, written inline inside a SQL query callback. The same handler decides, also inline, that an unknown email should result in silently creating a user account (:66-72) with a default password. In the report handler, the rule that only `'PAID'` payments count toward revenue lives at :108-110, inside the innermost of four nesting levels.
Impact: Two consequences, and the second is worse than the architectural one. Architecturally: none of these rules has an owner — a scheduled job, a second endpoint or a CLI that needs to enroll someone must copy the approval policy, the account-creation policy and the revenue criterion, and the copies will drift. For correctness: `cc.startsWith("4")` approves **any** string beginning with 4, with no gateway call, no funds check, no Luhn validation and no capture — "4" followed by anything is an approved purchase and a free enrollment. This is not a harmless stub, it is a forged payment authorization in production, made worse by the absence of rate limiting (API-04) and authentication (SEC-05).
Recommendation: T-07 — extract a payment service with an explicit interface (`authorize(card, amount)`) that talks to the real gateway and is injected into the controller, plus a checkout use case that orchestrates course → user → authorization → persistence. The revenue criterion becomes the responsibility of the payments model/repository (an aggregate query), not the handler. Implicit account creation must become an explicit, named decision of the use case.

### [HIGH] Connection constructed inside the class, plus module-level mutable state
ID: LAY-04
File: src/AppManager.js:7 (connection), src/utils.js:9-10 and :12-15 (global state), src/AppManager.js:59 (cache use)
Description: Three forms of the same problem. (1) The `AppManager` constructor does `this.db = new sqlite3.Database(':memory:')` — the class builds its own infrastructure dependency instead of receiving it, and the database path is a literal embedded in the constructor. (2) `utils.js` exports two mutable module-level variables: `globalCache = {}` (:9), written by `logAndCache` (:14) on every successful checkout, and `totalRevenue = 0` (:10). (3) `totalRevenue` is a number exported by value: importers receive a copy, so mutations would never propagate — the global accumulator is not merely a design problem, it cannot work, and in fact it is never mutated or read anywhere (see QUA-02).
Impact: No test can substitute a double for the database, because there is no injection point: any test of any rule requires a real SQLite instance, which is precisely why this project has no tests. `globalCache` is written under the key `last_checkout_${userId}`, never read, never invalidated and never bounded — it grows monotonically with the number of distinct users who check out, making it a slow memory leak on the application's hottest path. Mutable state shared across requests also makes the process impossible to scale horizontally without changing behavior.
Recommendation: T-09 — invert the dependency: the connection is created in the composition root from configuration (T-01) and injected into repositories; controllers receive repositories. Remove `globalCache` and `totalRevenue` (they have no consumer); if a cache is genuinely needed later, introduce it behind an injected interface with explicit size bounds and an invalidation policy.

### [HIGH] Inverted dependency direction: the data class registers the routes and receives the Express instance
ID: LAY-05
File: src/AppManager.js:25-26 and src/app.js:8-10
Description: `app.js`, which should be the composition root, delegates routing downward: it creates Express and passes the instance into `manager.setupRoutes(app)` (:10). `AppManager` — the class that imports the `sqlite3` driver (:1) and owns the connection — is what calls `app.post`/`app.get`/`app.delete` and defines the handlers. The dependency arrow points from the data layer to the web framework, the reverse of what the target architecture requires. Line :26, `const self = this`, is the symptom: the handlers are nested deep enough inside callbacks that the class's `this` must be captured by hand for the inner levels to still reach the connection (:54, :57).
Impact: There is no boundary left to respect: the layer that talks to the database also knows `req`, `res` and the router, so any attempt to reuse the data access outside an HTTP request drags Express along, and any route change is a change to the data module. The composition root loses its only job — assembling the application — and has no visibility into which routes exist; discovering the API surface requires reading the persistence class.
Recommendation: T-06 with T-09 — the composition root assembles: load config, create the connection, instantiate repositories and controllers, register the router. Routes are declared in `views/routes`, pointing at controller methods; controllers depend on repositories; repositories depend only on the connection they receive. No module below the routes imports Express again.

### [HIGH] A declined payment leaves a committed user account behind
ID: DAT-02
File: src/AppManager.js:66-72 (creation) with :46-48 (decline)
Description: When the email does not exist, the handler creates the user and only then calls `processPaymentAndEnroll` (:71). Inside it, `status` is computed at :46 and, if it is `"DENIED"`, :48 responds `400 "Pagamento recusado"` and returns. The user write at :69 has already been committed by the driver's autocommit at that point, and there is no rollback or compensating delete on any path. The same applies to the error paths at :51 and :55, which respond 500 over already-committed writes.
Impact: A declined checkout — an operation that failed and was reported to the client as a failure — leaves a permanent user account in the database, with the default password `123456` when `pwd` was not supplied (SEC-04). A client who retries with a different card takes the existing-user path and receives the enrollment bound to the account created on the previous attempt, carrying the first attempt's password. Since the route is public and unthrottled, this is also a vector for polluting the `users` table from anonymous requests using cards known to be declined.
Recommendation: T-10 — bring user creation into the same checkout transaction, with `ROLLBACK` on every error and decline path, so that a decline leaves no trace. Alternatively, separate registration from checkout entirely, so that creating an account stops being a side effect of a purchase.

### [HIGH] Deleting a user orphans enrollments and payments, and the schema has no foreign keys
ID: DAT-03
File: src/AppManager.js:131-137 (deletion) and :14-15 (schema without FKs)
Description: `DELETE /api/users/:id` runs `DELETE FROM users WHERE id = ?` and nothing else: there is no `ON DELETE` clause, no cascade and no manual cleanup of children. The schema declares relationships as plain integers — `enrollments(user_id INTEGER, course_id INTEGER)` (:14) and `payments(enrollment_id INTEGER, ...)` (:15) — with no `REFERENCES` at all, so there is no referential integrity to cascade; additionally SQLite requires `PRAGMA foreign_keys = ON` per connection, which is never executed. The code documents the defect in its own response: `res.send("Usuário deletado, mas as matrículas e pagamentos ficaram sujos no banco.")`.
Impact: After `DELETE /api/users/1`, the `enrollments` rows pointing at id 1 and the `payments` rows tied to those enrollments remain, now parentless. The financial report then renders them as `student: 'Unknown'` (:113) and keeps counting their revenue, so the platform's accounting contains lines that can no longer be attributed to anyone — and it is irreversible, because the user's name and email are gone. There is no way to reconstruct who paid.
Recommendation: T-11 — declare the foreign keys in the schema (`REFERENCES users(id)`, `REFERENCES courses(id)`, `REFERENCES enrollments(id)`) with a deliberately chosen delete policy, enable `PRAGMA foreign_keys = ON` when the connection is created, and decide in the use case between cascading deletion inside a transaction or — more appropriate for financial records — a logical delete (anonymization) that preserves enrollments and payments.

### [HIGH] Hand-rolled request lifecycle: the report either hangs or kills the process
ID: API-01
File: src/AppManager.js:80-129 (counters at :86, :93, :117-121; ignored errors at :92, :104, :106)
Description: The financial report coordinates N concurrent queries with two manual counters, `coursesPending` (:86) and `enrPending` (:93), and responds only when both reach zero (:98, :121). The inner callbacks declare an `err` parameter and never inspect it: at :92, if the enrollments query fails, `enrollments` arrives `undefined` and `enrollments.length` throws a `TypeError` — inside an asynchronous driver callback, outside Express's reach, which makes the exception uncaught and terminates the process. On paths where no exception occurs, the decrement simply never happens and the counter never reaches zero. There is also an observable effect on the success path: `report.push` (:96, :119) runs in callback-completion order, not course order.
Impact: Two failure modes, both worse than a 500: the request hangs until the client times out, holding the connection open and never responding, or the whole process dies on an uncaught exception and every concurrent caller loses their request. Neither is diagnosable from the log, because `err` was discarded. On the happy path, the same query returns courses in different orders between calls, so clients cannot rely on element position.
Recommendation: T-18 — eliminate the manual coordination: replace the callbacks with a promise-based API (`util.promisify` or a repository wrapper) and build the report from a single `await` over one aggregate query (see DAT-04), so that exactly one response point exists per request. Register a centralized error handler (T-14) and an `uncaughtException` handler so that no callback failure can silently take the process down.

### [HIGH] Input not validated at the boundary: one wrongly typed field kills the process
ID: API-03
File: src/AppManager.js:29-35 (read and check), :46 (use without a type check), :68 (credential default), :132 (path param)
Description: Checkout reads five body fields (`usr`, `eml`, `pwd`, `c_id`, `card`) and applies a single check: `if (!u || !e || !cid || !cc) return res.status(400)`. That is truthiness-based presence only — no type, format, length or range. Verifiable consequences in the code: `eml` is used as the user's identity key (:40) with no email-format validation and no `UNIQUE` constraint in the schema (:12); `cc` is used in `cc.startsWith("4")` (:46) with no type check, so a `"card": 4111222233334444` — a JSON number rather than a string, a trivial client mistake — throws `TypeError: cc.startsWith is not a function` inside the `db.get` callback, outside Express's reach; `pwd` is optional and silently replaced with `"123456"` (:68); `cid` is never validated as an integer; and `req.params.id` at :132 goes straight into the `DELETE` unvalidated. No validation library is declared in `package.json`.
Impact: Raised from MEDIUM on reachability: the route is public, unauthenticated and unthrottled, and the mistypeable field is on the main path. An exception thrown inside a `sqlite3` driver callback is not caught by Express — it surfaces as `uncaughtException` and terminates the Node process, so a single malformed POST from an anonymous client is a full denial of service rather than a 400. The remaining gaps produce silent corruption: duplicate accounts for the same email spelled differently, and accounts holding a publicly known password.
Recommendation: T-15 — validate the payload at the boundary with a declarative schema (type, email format, `pwd` required, card format and length, `c_id` a positive integer), rejecting with a 400 and a structured error body before any database access; make `pwd` required instead of defaulted; validate `:id` as an integer on the delete route; add `UNIQUE` on `users.email` in the schema. Also register the T-14 error handler, so that an unexpected error becomes a 500 rather than the death of the process.

### [MEDIUM] Configuration embedded in code, with no config module and no environment reads
ID: LAY-06
File: src/utils.js:1-7 (`port: 3000`, `smtpUser`), src/AppManager.js:7 (`':memory:'`), src/app.js:12 (port use)
Description: There is no configuration module and not one `process.env` read anywhere in the project, and no dotenv dependency is declared. Deployment choices sit as literals inside application files: port `3000` in the `config` object in `utils.js` (:6), the database path `':memory:'` inside the `AppManager` constructor (:7) and the mail sender `smtpUser` (:5). The file holding configuration is the same file holding the global cache and the hash function, so there is not even a nominal layer boundary. The credentials in that same object are covered by SEC-01 — the finding here is maintainability, not vulnerability.
Impact: No parameter can vary by environment without editing code and redeploying: bringing up a second instance on another port, or pointing the database at a persistent file instead of `:memory:`, requires editing `utils.js` and `AppManager.js` — the latter being the file that also contains every route and all the SQL, so a trivial infrastructure change touches the project's most sensitive module. The in-memory database also means every restart discards all data, a configuration choice that is invisible from the application code.
Recommendation: T-01 — create `config/` reading from `process.env` with safe development defaults and presence validation at boot, move port, database path and mail sender there, and inject configuration from the composition root instead of importing it inside domain modules.

### [MEDIUM] Two-level N+1 in the financial report
ID: DAT-04
File: src/AppManager.js:83-128 (outer loop :89, query :92; inner loop :102, queries :104 and :106)
Description: The report runs one query to list courses (:83) and then, inside the `forEach` over that result (:89), one enrollments query per course (:92). Inside the `forEach` over each enrollment set (:102), it runs two more per enrollment: one for the user (:104) and one for the payment (:106). The total is `1 + C + 2E` queries, where C is the number of courses and E the platform-wide number of enrollments — with 20 courses and 5,000 enrollments, 10,021 queries in a single HTTP request, all dispatched at once over the same connection.
Impact: The cost grows linearly with business volume, so the endpoint gets slower exactly as the platform succeeds. The queries are issued with no concurrency limit against a single SQLite connection, so each report call serializes thousands of operations and blocks the shared connection (LAY-04) used by every concurrent checkout — a report requested at peak hours degrades the payment flow. It is also what enables API-01: each of those thousands of queries is a callback that can fail and leave the manual counter undecremented.
Recommendation: T-12 — replace the whole structure with a single query `JOIN`ing `courses`, `enrollments`, `users` and `payments`, aggregating in the database, and build the response from that one result. The query count then becomes 1 regardless of volume, and the manual coordination of API-01 disappears with it.

### [MEDIUM] The report loads the entire platform into memory, unpaginated, aggregating in application code
ID: DAT-05
File: src/AppManager.js:83 (`SELECT * FROM courses`), :92 (`SELECT * FROM enrollments WHERE course_id = ?`), :108-110 (in-memory sum)
Description: `GET /api/admin/financial-report` accepts no pagination, limit, cursor or period parameter: it fetches every course, every enrollment of every course and, per enrollment, the user and the payment, accumulating everything in an in-memory `report` array before responding. `courses` grows moderately, but `enrollments` and `payments` grow with every sale — they are not bounded lookup tables. Revenue is summed in an application loop (`courseData.revenue += payment.amount`, :109) rather than by a `SUM()` in the database.
Impact: Response size and memory use grow without bound alongside sales history: a year of operation makes a single GET capable of materializing the complete enrollment and payment history in the process heap and serializing it into one JSON body, with no way for the client to ask for less. With no period filter, the report also stops being useful as a financial instrument — there is no way to ask for "last month". Loop aggregation moves work into Node that the database would do in one statement, multiplying the cost described in DAT-04.
Recommendation: T-13 — paginate and filter the endpoint (a required or default-bounded period, `limit`/`offset` or a cursor, with a server-enforced maximum) and move aggregation into SQL (`SUM(amount) ... WHERE status = 'PAID' GROUP BY course_id`), returning database-computed totals instead of raw rows summed in memory.

### [MEDIUM] Errors declared and never inspected, success reported over failure, no centralized error handler
ID: API-02
File: src/AppManager.js:57-61 (audit log), :92, :104, :106 (report), :133-136 (deletion); handler absent in src/app.js:5-10
Description: Five callbacks receive `err` and never consult it. At :57 the `audit_logs` INSERT fails silently and the handler responds `200 {msg: "Sucesso"}` regardless. At :133 the `DELETE` receives `err` and responds with success text whatever the outcome. At :92, :104 and :106 the ignored error is not merely lost: it leads to the hang or process death described in API-01. Where errors are handled, the handling is a generic string repeated by hand at each site (`"Erro DB"`, `"Erro Matrícula"`, `"Erro Pagamento"`, `"Erro ao criar usuário"`), with no log and no cause. No error middleware is registered in `app.js`, and `NODE_ENV` is set nowhere — so Express's default handler returns a stack trace to the client for any synchronous exception in a handler.
Impact: Persistence failures become invisible in both directions at once: the client receives success and the operator receives no log, so a lost audit row or a deletion that did not happen is undetectable after the fact. Because `err` is discarded, none of the DAT-01 and API-01 failures leaves a diagnosable trace. In the opposite direction, Express's default handler exposes file paths and internal structure to an anonymous caller. The duplicated generic messages guarantee drift as the code grows.
Recommendation: T-14 — register a centralized error middleware at the end of the chain that converts errors into structured responses with appropriate status codes, logs the cause through the T-23 logger and never includes a stack trace in the body; propagate errors via `next(err)` or promise rejection instead of ignoring them; handle each database callback's `err` explicitly for as long as those callbacks exist.

### [MEDIUM] Missing middleware chain: no rate limit on the route that accepts cards, no authentication, no error handler
ID: API-04
File: src/app.js:5-10
Description: The composition root registers exactly one middleware: `express.json()` (:6). There is no authentication or authorization middleware, despite the three routes including an admin report and a deletion (SEC-05); no centralized error handler (API-02); no rate limiting on `POST /api/checkout`, which accepts card numbers; no security headers; no request logging. Body size limit is not a finding here — `express.json()` applies a 100 kB default, and that was verified before reporting.
Impact: The missing rate limit on checkout is the most serious, because it compounds with the approval rule from LAY-02: an anonymous caller can submit cards in volume against an endpoint that answers `"Sucesso"` for any PAN starting with 4 and `"Pagamento recusado"` for the rest, which is a free, unthrottled card-testing oracle — and each declined attempt still leaves a user account in the database (DAT-02). The lack of request logging means that abuse would leave no trace. And with no cross-cutting layer, each such concern tends to be copy-pasted inside each handler as it gets implemented.
Recommendation: T-16 — introduce `middlewares/` and register on the composition root's chain: authentication and authorization (T-05), rate limiting specifically on the checkout and delete routes, structured request logging, security headers, and the centralized error handler as the last middleware. Registration order then becomes explicit in one place.

### [MEDIUM] Inconsistent response contract, and success reported for an operation that may not have happened
ID: API-05
File: src/AppManager.js:35, :38, :41, :48, :51, :55, :70, :84 (plain-text errors) vs :60, :87, :98, :121 (JSON success); :135 (unconditional success)
Description: Every error path responds with plain text via `res.send` — `"Bad Request"`, `"Curso não encontrado"`, `"Erro DB"`, `"Pagamento recusado"`, `"Erro Matrícula"` — while every success path responds with JSON (`{msg, enrollment_id}` at :60, an array at :87/:98/:121). `DELETE /api/users/:id` responds `200` with the sentence `"Usuário deletado, mas as matrículas e pagamentos ficaram sujos no banco."` without checking `err` and without checking whether any row was affected. Checkout, which creates resources, responds `200` rather than `201`, and a payment decline responds `400` — a client-error class — for what is a payment-provider decision.
Impact: Raised from LOW because it contains a correctness bug, not only a formatting one: a `DELETE` of a nonexistent id, or one that failed in the database, returns `200` and the word "deletado" — the client concludes the operation happened when it did not, with no way to distinguish the cases. As for the rest, a client cannot handle errors programmatically: it must branch on `Content-Type` per path and parse Portuguese sentences to work out what happened, so any wording change breaks integrations. Error messages also carry no stable code.
Recommendation: T-17 — standardize a single JSON error envelope (`{error: {code, message, details}}`) emitted by the centralized error handler from T-14, and revise the status codes: `201` with `Location` on enrollment creation, `402`/`422` for a payment decline, `404` when the `DELETE` affected no rows, `204` when it did. The sentence at :135 that documents the integrity bug goes away with the DAT-03 fix.

### [LOW] `SELECT *` where only a few columns are used
ID: DAT-06
File: src/AppManager.js:37, :83, :92
Description: Three queries load the whole entity and use two or three columns: :37 runs `SELECT * FROM courses WHERE id = ?` and reads `price` (:54) and `title` (:59); :83 runs `SELECT * FROM courses` and reads `id` (:92) and `title` (:90); :92 runs `SELECT * FROM enrollments WHERE course_id = ?` and reads `id` (:106) and `user_id` (:104). The queries that do name columns explicitly (:40, :104, :106) show the correct form is already known in the same file. Verified that no sensitive column is dragged into a response this way — the `users` table, the only one with a sensitive column, is always queried by explicit column — so this is LOW and not SEC-02.
Impact: The immediate cost is small; the coupling is not. The layer consuming these queries depends on the full schema, so adding or renaming a column in `courses` or `enrollments` changes what these sites receive even though nothing asked for the new field — and that is precisely how a sensitive column added later leaks through a path that is harmless today. At :83 the `SELECT *` is also multiplied by the volume described in DAT-05.
Recommendation: T-13 — enumerate the columns each query actually uses; when consolidating the report into a single aggregate `JOIN` (T-12), project only the fields that make up the response.

### [LOW] Dead code: global state never read, credentials never referenced, a table never queried
ID: QUA-02
File: src/AppManager.js:2 (import), src/utils.js:9-10, :25, :2-3, :5; src/AppManager.js:16 and :57 (audit_logs)
Description: Four groups, each confirmed by grep across `src/`. (1) `totalRevenue` is imported at `AppManager.js:2`, never used in that file, never mutated anywhere, and exported by value at `utils.js:25` — were it ever mutated, importers would not see the change (see LAY-04). (2) `globalCache` is written at `utils.js:14` on every checkout and read by no code at all. (3) The `config` keys `dbUser`, `dbPass` and `smtpUser` are referenced nowhere — they are dead credentials, which does not make them safe (SEC-01) but changes the fix to deletion. (4) The `audit_logs` table is created (:16) and written (:57) and never read by any query.
Impact: Each item misleads the reader about what the system does. `globalCache` and `audit_logs` look like a working cache and a working audit trail — a reviewer concludes that checkout is traceable and that there is a cache to invalidate, when neither is consumed; in the case of `audit_logs`, the write costs an INSERT on the critical payment path (DAT-01) to produce data nobody queries. The dead credentials suggest database and mail integrations that do not exist, inflating the system's apparent surface.
Recommendation: T-21 — remove `totalRevenue`, `globalCache` and the three unused configuration keys. For `audit_logs`, decide explicitly: if the audit trail is a requirement, expose it through a use case that reads it and move it out of the payment transaction; if it is not, remove both the table and the INSERT.

### [LOW] Magic numbers and inline literals in business rules and in the hash

### [LOW] Names that carry no information, and nesting that prevents review
ID: QUA-04
File: src/AppManager.js:29-33, :26, :43, :83-128, :37-77; src/utils.js:12, :17; src/AppManager.js:4
Description: The checkout handler renames five request fields to letters and abbreviations: `u`, `e`, `p`, `cid`, `cc` (:29-33) — and `e` conceptually collides with the `err` used in the callbacks immediately below. The public contract's own keys are abbreviated (`usr`, `eml`, `pwd`, `c_id`, `card`), forcing callers to guess. `AppManager` (:4) names a manager of nothing; `logAndCache` (utils:12) declares two responsibilities joined by "and"; `badCrypto` (utils:17) admits the defect in its name. `const self = this` (:26) exists only to work around `this` rebinding in the nesting. ### [LOW] Ad-hoc logging through `console.log`, conflated with a cache write
ID: QUA-05
File: src/utils.js:12-15 (`logAndCache`), called at src/AppManager.js:59
Description: The project's only observability mechanism is `console.log`. `logAndCache` (:12-15) prints `[LOG] Salvando no cache: ${key}` to stdout and, in the same function, writes to `globalCache` — the name admits both responsibilities, and the write targets the global state of LAY-04, whose contents are never read (QUA-02). There is no level, timestamp, request correlation or structure, and no logging library is declared. The startup banner at `app.js:13` is not a finding (deliberate initialization output), and the `console.log` at `AppManager.js:45` is filed as SEC-02, not here, because it prints a secret.
Impact: There is no way to adjust verbosity per environment, filter by severity or correlate lines to a request, and the output is not parseable by any collector — which means the discarded errors of API-02 leave no record, not even an informal one. The conflated function also makes it impossible to log without writing to the cache: any site that merely wants to record something ends up feeding a map that grows without bound.
Recommendation: T-23 — introduce a structured logger with levels (pino, winston, or a minimal wrapper over `console` carrying level and timestamp), injected as a dependency; separate logging from the cache write by dissolving `logAndCache` — and since the cache has no consumer, remove the cache half under T-21.

## Notes

- **No deprecated APIs found.** Checked against Node.js (no version pinned by the project; local runtime v24.10.0), Express 4.22.1 and `sqlite3` 5.1.7. Specifically checked: `Buffer.from()` at `utils.js:20` is the current form, not the deprecated `new Buffer()`; `express.json()` at `app.js:6` is current and there is no redundant `body-parser` dependency; `require('sqlite3').verbose()`, `db.serialize()`, `db.run/get/all` with placeholders and `this.lastID` are the documented, supported API of the pinned version; no use of `url.parse()`, `crypto.createCipher`, `fs.exists`, `util.is*` or the `domain` module. This is a verified "none", not a gap.
- **There is no SQL injection.** All thirteen queries use `?` placeholders with bound parameters; none assembles statement text by concatenation or interpolation. The one template literal near SQL, at `AppManager.js:57`, builds the *value* passed as a bound parameter (`[\`Checkout curso ${cid} por ${userId}\`]`), not the statement text — it is safe, and it is recorded here because it is exactly the kind of line a keyword sweep would report as a false positive.
- **Express 4 while Express 5 is available** is a maintenance observation, not a deprecation: the project declares `^4.18.2` and the lock resolves 4.22.1, a supported version. Migrating to the 5.x line is a decision separate from this report.
- **No automated tests** in the project: no test framework, no `devDependencies` and no test script in `package.json`. This is not a code finding — there is no line to point at — but it matters for Phase 3: validation will depend on replaying the endpoints against a captured baseline rather than on an existing suite. LAY-04 explains why no unit test would be viable in the current state.
- **No migrations, and an in-memory database.** Schema and seeds are created inline at boot (`AppManager.js:11-22`) over `sqlite3` `:memory:`, so there is no schema-evolution path and every restart discards all data. The DAT-03 fix (foreign keys) will require editing the inline DDL, which is feasible precisely because there is no persisted data to migrate.
- **`node_modules/` is not installed** at the time of this audit; the versions reported here come from `package-lock.json`. Phase 3 will need `npm install` before any validation. Operational risk to keep in mind: `sqlite3` 5.1.7 is a native module and may have no prebuilt binary for the Node 24 ABI, falling back to compiling from source.
- **Two findings were confirmed by reading and await empirical verification in Phase 3**, both concerning exceptions thrown inside asynchronous `sqlite3` driver callbacks (outside Express's error handling) terminating the process: `cc.startsWith` over a numeric `card` (API-03) and `enrollments.length` over an `undefined` result after a query error (API-01). The Phase 3 baseline capture will exercise both cases before any code changes.
