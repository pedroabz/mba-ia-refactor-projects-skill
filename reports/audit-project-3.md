## Findings

### [CRITICAL] Passwords hashed with unsalted MD5 and verified by string equality
ID: SEC-04
File: `models/user.py`:27-32 (write and verify paths); `seed.py`:19, 26, 33 (seeded through the same path)
Description: `set_password()` stores `hashlib.md5(pwd.encode()).hexdigest()` — a single pass of a fast general-purpose digest, with no per-user salt and no work factor. `check_password()` re-hashes the candidate and compares with `==`. The `password` column (`models/user.py`:11) therefore holds a bare MD5 digest for every account, including the three seeded users whose passwords are `1234`, `abcd` and `pass`. Nothing in the project uses a password KDF; the hashing is hand-rolled in the model.
Impact: Unsalted MD5 is reversible for any realistic password by rainbow table — the three seeded digests are in every public lookup table — and identical passwords produce identical digests, so one disclosed digest compromises every account sharing it. MD5 is fast enough that offline brute force proceeds at billions of guesses per second, and the 4-character minimum enforced at `routes/user_routes.py`:64 puts the entire allowed password space within seconds of exhaustive search. The `==` comparison additionally leaks timing information on the digest.
Recommendation: T-03 — replace with a password KDF (`werkzeug.security.generate_password_hash` / `check_password_hash`, already available through Flask's own dependency tree, or bcrypt/argon2), keep `set_password`/`check_password` as the only entry points so the seed stays consistent, and raise the minimum password length. Existing digests cannot be migrated — they must be invalidated and reset.

### [CRITICAL] Stored password hash returned in the response body of four endpoints
ID: SEC-02
File: `models/user.py`:21 (`'password': self.password` inside `to_dict()`); returned by `routes/user_routes.py`:33 (`GET /users/<id>`), :85-86 (`POST /users`), :129 (`PUT /users/<id>`), :209 (`POST /login`)
Description: `User.to_dict()` includes the `password` column, and four handlers return that serializer verbatim. `GET /users` is the only user-facing endpoint that does not leak it, because `routes/user_routes.py`:15-23 hand-builds a different dict that happens to omit the field — the omission is accidental, not a policy. None of the four leaking endpoints requires authentication (see SEC-05).
Impact: Any unauthenticated caller retrieves the MD5 digest of any account by `GET /users/<id>`, and combined with SEC-04 that digest is equivalent to the password. The login response hands the caller its own digest, and `PUT /users/<id>` hands back the digest of an account the caller may not own. This converts a weak-hashing finding into a remote full-account-compromise path with no credentials required.
Recommendation: T-04 — remove the field from the serializer, and move response shaping out of the model entirely (see LAY-03) so a single presentation layer decides what is public. The model-level leak is the reason four endpoints are affected by one line.

### [CRITICAL] No authentication or authorization anywhere; the issued token is never verified
ID: SEC-05
File: `routes/user_routes.py`:185-211 (`POST /login`, token minted at :210); absence confirmed across `app.py`:1-34 (no `before_request`, no auth extension) and all 18 route handlers in `routes/`
Description: `POST /login` returns `'token': 'fake-jwt-token-' + str(user.id)` — a guessable, unsigned string that is never read, decoded or checked by any code in the project. `grep` finds no authorization check in any handler and no guard middleware in the composition root. `User.is_admin()` (`models/user.py`:34-38) and the `role` column exist and are never called anywhere, so the three roles the schema distinguishes (`user`, `admin`, `manager`) carry no privilege. Reachable without credentials: `DELETE /users/<id>` (`routes/user_routes.py`:134, which also deletes that user's tasks), `DELETE /tasks/<id>` (`routes/task_routes.py`:225), `DELETE /categories/<id>` (`routes/report_routes.py`:211), `PUT /users/<id>` including the `role` field (`routes/user_routes.py`:119-122), `GET /users` (`routes/user_routes.py`:10, bulk personal data), and `GET /reports/summary` (`routes/report_routes.py`:12, per-user productivity on every user).
Impact: Every destructive and every data-exposing operation is open to the internet. An anonymous caller can delete any user along with all their tasks, delete any task or category, promote any account to `admin` through `PUT /users/<id>`, and enumerate every user's email, hash and productivity record. Because the token is never verified, there is nothing to bypass — the system has no access control to defeat, so the role column is documentation rather than enforcement.
Recommendation: T-05 — issue a signed token (JWT via a vetted library, or Flask's signed session), add authentication middleware that resolves the caller on every request, and apply deny-by-default authorization decorators on the destructive and bulk-read routes, routing admin-only operations through the existing `role` field. Combine with T-16 (middleware chain) so the check is registered once rather than copied into 18 handlers.

### [CRITICAL] Werkzeug interactive debugger shipped enabled on all interfaces, plus unrestricted CORS
ID: SEC-06
File: `app.py`:34 (`app.run(debug=True, host='0.0.0.0', port=5000)`); `app.py`:15 (`CORS(app)`)
Description: The shipped entry point enables `debug=True` while binding to `0.0.0.0`. Flask's debug mode activates the Werkzeug interactive traceback console, which evaluates arbitrary Python submitted through the browser on any unhandled exception, and `host='0.0.0.0'` makes that console reachable from every network interface rather than loopback. `README.md` documents `python app.py` as the way to run the application, so this is the operating configuration, not a local override. Separately, `CORS(app)` with no arguments applies `Access-Control-Allow-Origin: *` to every route including `POST /login` and all destructive endpoints.
Impact: This is remote code execution, not a tidiness issue. Any reachable client that can trigger an exception — and `routes/task_routes.py`:113 raises `TypeError` on a non-numeric `priority`, see API-03 — gets a console that runs code as the application user, which on this project means read and write access to `tasks.db` and the host filesystem. The debugger PIN raises the cost but is derived from host-stable values and is not a security boundary. The wildcard CORS policy independently lets any origin drive the unauthenticated destructive endpoints from a victim's browser.
Recommendation: T-01 — read the debug flag from the environment with a safe default of off, bind to `127.0.0.1` for local development, and run behind a WSGI server in any deployed context. Replace `CORS(app)` with an explicit origin allowlist. Per `deep/security.md`, severity is raised from the family's base HIGH to CRITICAL because an interactive debugger is reachable on a non-local interface.

### [CRITICAL] Hardcoded secrets in application modules
ID: SEC-01
File: `app.py`:13 (`SECRET_KEY = 'super-secret-key-123'`); `services/notification_service.py`:9-10 (`email_user = 'taskmanager@gmail.com'`, `email_password = 'senha123'`)
Description: Two credentials are literals in version-controlled application code. `SECRET_KEY` is the value Flask uses to sign session cookies and any `itsdangerous` token. The SMTP username and password sit in `NotificationService.__init__`, which also hardcodes the host and port. There is no config module and no environment read anywhere in the project, although `python-dotenv` is a declared dependency (`requirements.txt`:6) that is never imported — the intent existed and was abandoned.
Impact: A known `SECRET_KEY` lets anyone forge signed session cookies and any future signed token, so it must be treated as compromised the moment the repository is readable. The SMTP credential would grant send-as access to the mailbox. Both values are committed, so rotating them requires a code change and a redeploy rather than a config change, and the old values remain in git history permanently. Per `deep/security.md`, the SMTP credential is still a finding despite `NotificationService` having zero call sites — a committed password does not become safe by being dead code — though that does change the fix: the file should be deleted rather than refactored (see QUA-02).
Recommendation: T-01 — move both to environment variables loaded through a `config/` module, commit a `.env.example` with placeholder values only, add `.env` to `.gitignore`, and rotate anything that was ever real. Note honestly: these particular values are placeholder-grade (`senha123`, `super-secret-key-123`), so the immediate exposure is low and the finding is the pattern — but the pattern is what ships a live key the first time this code reaches an environment that has one.

### [CRITICAL] God files: three route modules each hold routing, validation, business rules, persistence and serialization
ID: LAY-01
File: `routes/task_routes.py`:1-299; `routes/user_routes.py`:1-211; `routes/report_routes.py`:1-223 (733 of the project's 1,158 lines)
Description: Each route module mixes five responsibilities that the MVC target assigns to four different layers. Taking `routes/task_routes.py` as the representative case: routing (`@task_bp.route` at :11, :65, :85, :156, :225, :240, :273), request validation (:89-124, :166-213), business rules (overdue determination :30-39 and :71-80, statistics aggregation and completion rate :273-297), persistence (`db.session.add/commit/rollback/delete` at :147-154, :217-223, :231-238, and 17 `Model.query` call sites), and response serialization (manual dict assembly :17-28, :162-169). No handler delegates — each one performs the whole operation inline, so the module is not a conventional thin routing file. The same mix is present in `routes/user_routes.py` (validation :54-72, rules :171-180, persistence :80-90, :127-132, :144-151, serialization :15-23, :162-169) and `routes/report_routes.py` (aggregation :15-68 and :111-152, persistence :182-223, serialization :70-99, :137-153).
`routes/report_routes.py` raises the severity independently on domain count: the module named for reports also owns the complete `Category` CRUD surface (:157-223 — list, create, update, delete), so it spans three entities and two unrelated concerns, and every change to category handling touches the reporting file.
Impact: There is no unit of this system that can be tested or changed in isolation. Validating a task requires a live Flask request context, a database and an HTTP client; changing how overdue is decided means editing a file that also wires routes and commits transactions. Because the handlers own the rules, a second caller — a scheduled overdue-notification job, a CLI import, a second endpoint — has no way to reuse them except by copying, which is exactly what has already happened six times (see QUA-01). Merge conflicts concentrate in three files that every feature must touch.
Recommendation: T-06 — split each module along the responsibility seams: thin blueprints in `views/` that only map URLs to callables, controllers in `controllers/` that read the request and choose status codes, domain rules on the models or in `services/`, and data access behind a repository or model methods. The line ranges above are the extraction boundaries; apply T-07 and T-08 to place what comes out.

### [HIGH] Business rules implemented inside route handlers
ID: LAY-02
File: `routes/task_routes.py`:30-39, :71-80, :281-296; `routes/user_routes.py`:171-180; `routes/report_routes.py`:30-68, :119-152
Description: Four domain rules live in handler bodies rather than in any layer a second caller could reach. (1) *Is a task overdue* — `due_date < utcnow()` combined with `status not in (done, cancelled)` — is decided inline at five of the six locations above. (2) *Completion rate* — `round((done / total) * 100, 2)` with a zero guard — is computed in the handler at `routes/task_routes.py`:296, `routes/report_routes.py`:67 and :151. (3) *Per-user productivity*, the loop at `routes/report_routes.py`:53-68 that counts each user's tasks and derives their rate. (4) *Priority classification* — the mapping of `1..5` onto `critical/high/medium/low/minimal` at `routes/report_routes.py`:83-89, and the separate rule that `priority <= 2` means high priority at :129 — two encodings of the same domain concept, both inline in the reporting handler.
Applying the test from `deep/layering.md`: each of these would have to be copied by any other caller to behave consistently. A nightly job that emails overdue tasks could not ask the system what "overdue" means; it would reimplement the comparison and could drift from the API.
Impact: The rules are unreachable outside an HTTP request and untestable without one, and they have already duplicated — the overdue rule exists in six places, and the two priority encodings in the same file disagree about where "high" ends (the label mapping calls `2` *high*; the threshold at :129 counts `1` and `2` together as high priority). Changing a rule means auditing three files and hoping no copy was missed.
Recommendation: T-07 — move each rule to the layer that owns it: overdue onto `Task` (where `is_overdue()` already exists, see QUA-01), completion rate and productivity aggregation into a reporting service, and the priority scale into a single named mapping the model and the reports both read. Handlers keep request parsing, status-code selection and response shaping.

### [HIGH] Models own the HTTP response contract
ID: LAY-03
File: `models/user.py`:16-25; `models/task.py`:23-36; `models/category.py`:13-21
Description: All three models expose `to_dict()` methods that assemble dictionaries shaped for the JSON response — stringifying datetimes to the API's format (`str(self.created_at)`), splitting the stored `tags` column into a list for the client (`models/task.py`:35), and deciding which columns the API exposes. This is the serialization-in-the-data-layer variant of LAY-03: persistence decides the API contract. The predicted consequence is already present in the code — because one serializer cannot serve endpoints that need different shapes, four handlers hand-build their own task or user dicts instead (`routes/task_routes.py`:17-28 and :162-169 via `routes/user_routes.py`, `routes/user_routes.py`:15-23 and :162-169, `routes/report_routes.py`:38-43, :138-142), duplicating field-by-field what `to_dict()` already does.
Impact: The API contract cannot change without editing the persistence layer, and a column added to a model silently appears in every response that uses its serializer. This coupling is the direct mechanism of the CRITICAL leak in SEC-02: one `'password'` key in `models/user.py`:21 exposes the hash from four unrelated endpoints, and no handler that returns `to_dict()` can opt out. The workaround — hand-built dicts — has produced four divergent shapes for the same `Task` entity (see API-05), so clients cannot rely on any one of them.
Recommendation: T-08 — move serialization out of the models into an explicit presentation step (marshmallow schemas, already a declared but unused dependency, or plain serializer functions in the controller layer), with separate public and internal shapes for `User`. Keep on the models only what derives from the entity's own fields and invariants.

### [HIGH] Layer bypass: handlers drive the session directly, and the composition root runs DDL at import
ID: LAY-05
File: `app.py`:9-31 (module-level app, config, route definitions, import-time `db.create_all()`); `routes/task_routes.py`:2 + :147-154, :217-223, :231-238; `routes/user_routes.py`:2 + :80-90, :127-132, :140-151; `routes/report_routes.py`:2 + :182-223
Description: Two reversed arrows. *Downward:* all three route modules import the ORM session (`from database import db`) and execute unit-of-work operations — `db.session.add`, `commit`, `delete`, `rollback` — directly in handler bodies, across 57 `Model.query` call sites. There is no repository or data-access layer between the HTTP boundary and the session, so the presentation layer is also the persistence layer. *Upward and sideways:* `app.py`, whose job is to assemble the application, additionally holds configuration literals (:11-13), defines two route handlers of its own (:22-28), and executes schema DDL at import time inside a module-level `app_context()` (:30-31). The app object itself is created at module level (:9) rather than by a factory.
Impact: Because `app` is a module-level singleton with import-time side effects, importing anything from `app.py` creates the schema — `seed.py`:2 does exactly this, so running the seed script has the side effect of creating `tasks.db`. There is no way to construct a second application instance pointed at an in-memory database, which means no test can run without touching the real SQLite file; this is the concrete cost of the missing factory, more than any abstract dependency rule. And with the session reachable from every handler, nothing prevents the next handler from committing mid-validation; the layer boundary exists only as a directory name.
Recommendation: T-06 to extract the data-access operations behind model or repository methods that controllers call, and T-09 to replace the module-level app with a `create_app(config)` factory that registers blueprints and leaves schema management to an explicit command rather than import time (see DAT-X).

### [MEDIUM] Referential integrity on delete is accidental, not declared — and bypassed by bulk deletes
ID: DAT-03
File: `routes/report_routes.py`:211-223 (`DELETE /categories/<cat_id>`); schema at `models/task.py`:14, :21; bulk-delete path at `seed.py`:11-13; contrast with `routes/user_routes.py`:140-143
Description: **Corrected after empirical verification — the first draft of this finding overstated the impact and is restated here.** `delete_category` removes the `Category` row with no cleanup of the tasks referencing it. Checking the three places `deep/data-access.md` requires: the relationship `db.relationship('Category', backref='tasks')` (`models/task.py`:21) declares no `cascade` and no `passive_deletes`; the column (`models/task.py`:14) declares no `ondelete`; the handler performs no manual cleanup. The generated DDL confirms `FOREIGN KEY(category_id) REFERENCES categories (id)` with no `ON DELETE` clause, and `PRAGMA foreign_keys` reads `0`, so SQLite does not enforce the constraint at all.
What was verified rather than assumed: `db.session.delete(category)` **does** leave the children intact, because SQLAlchemy's default unit-of-work behaviour loads the `tasks` collection and issues `UPDATE tasks SET category_id = NULL`. A probe against the live database confirmed the child's `category_id` becomes `None`, and the baseline capture (`.refactor-arch/baseline.json`, `tasks.get.orphaned`) records the same. So there are **no dangling ids through the HTTP path**, and the claim that surviving rows point at a deleted row was wrong.
The finding that remains is that this correct outcome is accidental. It holds only while every delete goes through the ORM with the collection loaded; the schema expresses no policy and the database enforces none. The same probe confirmed the other path: `Category.query.filter_by(id=...).delete()` — a bulk delete, which bypasses the unit of work — leaves `category_id = 5` pointing at a row that no longer exists, with nothing to prevent it. The project already uses exactly that construct at `seed.py`:11-13.
Impact: Two concrete consequences. First, the de-categorization is a silent policy decision nobody made: deleting a category wipes the classification from every task that used it, reported identically to a task that was never categorized, with no confirmation and no way to refuse. Second, the integrity guarantee is one refactor away from failing — any future bulk delete, raw SQL, or `passive_deletes` optimization produces dangling ids immediately, and because FK enforcement is off the database will accept them silently. The nullifying `UPDATE` is also unbounded: deleting a widely used category rewrites every task row referencing it in one statement.
Recommendation: T-11 — declare the policy in the schema instead of inheriting it from ORM defaults: `ForeignKey('categories.id', ondelete='SET NULL')` if silent de-categorization is intended, or `RESTRICT` with a `409` response if a category in use should not be deletable. Enable `PRAGMA foreign_keys=ON` in the connection factory, since a declared constraint that is never enforced is not a fix. Apply the same explicit review to the manual task cleanup in `delete_user`, which works but relies on the handler remembering to do it.

### [MEDIUM] One domain rule reimplemented six times while the method that implements it is never called
ID: QUA-01
File: Overdue rule: `routes/task_routes.py`:30-39, :71-80, :284-287; `routes/user_routes.py`:171-180; `routes/report_routes.py`:34-37, :132-135 — against `models/task.py`:50-60 (`Task.is_overdue()`, zero call sites). Validation: `routes/task_routes.py`:96-124 and :166-213 — against `utils/helpers.py`:57-108 (`process_task_data()`, zero call sites) and `models/task.py`:38-48 (`validate_status`, `validate_priority`, zero call sites). Enum lists: `routes/task_routes.py`:110, :177; `models/task.py`:39; `utils/helpers.py`:75, :110. Completion rate: `routes/task_routes.py`:296; `routes/report_routes.py`:67, :151 — against `utils/helpers.py`:14-17 (`calculate_percentage()`, imported at `routes/report_routes.py`:7 and never invoked).
Description: This is the abandoned-abstraction form of the finding, in four instances. The overdue predicate is written out as a three-level nested conditional in six places across three files; `Task.is_overdue()` implements exactly the same rule and is called from nowhere. Task field validation is written inline twice; `utils/helpers.process_task_data()` implements all of it — title bounds, status enum, priority range with an integer cast, date parsing, tag joining — in 52 lines that nothing calls, and the two model validator methods are likewise dead. The valid-status list appears in five places. The percentage calculation appears three times while `calculate_percentage` is imported into the reporting module and never used. The right answer is already written, four times over, and ignored.
Impact: Changing any of these rules requires finding every copy. Adding a `blocked` status means editing five lists; changing what counts as overdue means editing six nested conditionals and remembering the dead model method. Severity is held at the family base of MEDIUM rather than raised, because the six overdue copies are byte-for-byte equivalent in behaviour; it would be HIGH if they had diverged.
Recommendation: T-19 — make each rule single-sourced and then delete the copies: call `Task.is_overdue()` from every site, promote the status and role lists to named constants that the models and the validation layer both import, and route all task-field validation through one schema. Prefer salvaging the existing abstractions over writing new ones — the uncalled code is largely correct, and `process_task_data()` already handles the integer cast that the inline copies omit (see API-03).

### [MEDIUM] N+1 query patterns in four list and report endpoints
ID: DAT-04
File: `routes/task_routes.py`:41-57 (`GET /tasks`); `routes/user_routes.py`:22 (`GET /users`); `routes/report_routes.py`:163 (`GET /categories`); `routes/report_routes.py`:53-56 (`GET /reports/summary`)
Description: Four endpoints query inside a loop over the results of a previous query, in three of the shapes `deep/data-access.md` lists. *Explicit:* `GET /tasks` loads all tasks, then issues `User.query.get()` and `Category.query.get()` per row (`routes/task_routes.py`:42, :51) — 1 + 2N queries, N = total tasks, with the same user and category fetched repeatedly. `GET /categories` issues `Task.query.filter_by(category_id=c.id).count()` per category — 1 + N. `GET /reports/summary` issues `Task.query.filter_by(user_id=u.id).all()` per user (`routes/report_routes.py`:56) — 1 + N on top of the 15 separate count queries at :15-28, and loads every one of that user's full task rows to count two statuses in Python. *Implicit:* `GET /users` accesses `len(u.tasks)` per row (`routes/user_routes.py`:22), which lazy-loads each user's complete task collection — 1 + N queries that transfer every column of every task to produce a single integer.
Impact: Request cost grows linearly with table size instead of staying bounded. With 500 tasks across 50 users, `GET /tasks` issues 1,001 queries and `/reports/summary` issues 66 while materializing every task row twice. The relationship-based count in `GET /users` is the worst value for money — full row transfer for a number the database can produce in one aggregate. Combined with the absent pagination in DAT-05, these endpoints degrade in proportion to usage, and the ORM hides it: none of the four handlers contains a visible query loop that a reader would flag.
Recommendation: T-12 — eager-load the relations `GET /tasks` needs (`joinedload`/`selectinload` on `user` and `category`), replace per-row counts with a single grouped aggregate (`func.count` with `group_by`) for `GET /categories`, `GET /users` and the productivity section of `/reports/summary`, and collapse the 15 status/priority counts at `routes/report_routes.py`:15-28 into one grouped query each. This belongs in the data-access layer extracted by T-06, not back in the handlers.

### [MEDIUM] Collection endpoints fetch entire tables with no pagination
ID: DAT-05
File: `routes/task_routes.py`:14 (`GET /tasks`), :266 (`GET /tasks/search`), :281 (`GET /tasks/stats`); `routes/user_routes.py`:12 (`GET /users`), :35 (`GET /users/<id>`), :159 (`GET /users/<id>/tasks`); `routes/report_routes.py`:30 (`GET /reports/summary`), :109 (`GET /reports/user/<id>`)
Description: Eight handlers call `.all()` with no `limit`, `offset` or cursor, and no endpoint in the project accepts a pagination parameter. The affected collections are `tasks` and `users`, both of which grow without bound in a task manager — unlike `categories`, which is a classification table bounded by design and correctly fetched whole at `routes/report_routes.py`:159. `GET /tasks/search` (:240-271) builds filters but applies no limit, so an empty query string returns the entire table. Two sites are the *counting-in-application-code* variant: `routes/task_routes.py`:281-287 loads every task to count overdue ones in a Python loop, and `routes/report_routes.py`:30-43 does the same while also building an unbounded `overdue_list` embedded in the summary response.
Impact: Response size and memory use scale with the table. The overdue list inside `/reports/summary` has no cap at all, so a backlog of ten thousand overdue tasks becomes a single ten-thousand-element JSON array in one response — the report endpoint degrades fastest precisely as the data it reports on becomes interesting. Clients have no way to request a page, so every consumer must download everything, and the N+1 multipliers from DAT-04 apply to the full table rather than to a page.
Recommendation: T-13 — add `limit`/`offset` (or keyset) pagination with a sane default and a hard maximum to every collection endpoint, return the total count alongside the page, and push the overdue counting into the database as a filtered `count()` instead of a Python loop. Cap the embedded `overdue_list` or move it behind its own paginated endpoint.

### [MEDIUM] Twelve bare `except:` clauses and no centralized error handler
ID: API-02
File: `routes/task_routes.py`:62-63, :137, :204, :236; `routes/user_routes.py`:130, :149; `routes/report_routes.py`:186, :207, :221; `utils/helpers.py`:46, :49, :88
Description: Both halves of this finding are present. *Swallowed:* twelve bare `except:` clauses catch everything and discard the exception object. The worst is `routes/task_routes.py`:62-63, which wraps the entire `GET /tasks` body — any failure in 50 lines of serialization, lookup and overdue logic returns `{'error': 'Erro interno'}`, 500, with the cause neither logged nor re-raised. In Python a bare `except:` also catches `KeyboardInterrupt` and `SystemExit`, so these handlers swallow shutdown signals. Four more sites catch, print to stdout and return a generic message (`routes/task_routes.py`:151-154, `routes/user_routes.py`:87-90), which loses the traceback even when the message survives. *Structural:* there is no `@app.errorhandler` anywhere in `app.py`; instead ten handlers each wrap themselves in try/except with their own hand-written generic message (`'Erro ao atualizar'`, `'Erro ao deletar'`, `'Erro ao criar categoria'`), which is duplication that guarantees drift.
Impact: Diagnosis is impossible from outside: a 500 from `GET /tasks` could be a missing column, a `None` comparison, or a disk error, and the server keeps no record of which. Operators have nothing to search. Meanwhile the paths *not* wrapped leak the opposite way — the `TypeError` from a non-numeric `priority` (`routes/task_routes.py`:113, see API-03) is uncaught, and with `debug=True` (SEC-06) Flask answers it with a full interactive traceback instead of a 500.
Recommendation: T-14 — register centralized `@app.errorhandler` handlers that log the exception with its traceback and return one consistent error envelope, then delete the per-handler try/except blocks. ## Notes

- **Three findings were confirmed empirically during the Phase 3 baseline capture**, and one was corrected. The 77-call baseline in `.refactor-arch/baseline.json` records: `GET /users/1` returning `"password": "81dc9bdb52d04dc20036dbd8313ed055"`, which is the MD5 of `1234` and appears in every public rainbow table (SEC-02 + SEC-04); the three type-unsafe inputs of API-03 returning a **20 KB HTML body instead of JSON**, which is the Werkzeug interactive debug console being served to the client exactly as SEC-06 predicted; and `POST /login` returning `fake-jwt-token-1` (SEC-05). The correction is DAT-03, restated above.
- **Transaction findings checked and not confirmed.** DAT-01 and DAT-02 were investigated and are **not** findings here, which is worth stating because the code looks like both. `delete_user` (`routes/user_routes.py`:140-151) issues N+1 writes — every task of the user, then the user — and `update_task`/`update_user` mutate attributes while validations can still return 400 between them. Per `deep/data-access.md`, the driver's default settles it: the Flask-SQLAlchemy session is a single transaction terminated by one `commit()`, so the multi-row delete is already atomic, and Flask-SQLAlchemy 3.1 registers a `teardown_appcontext` hook that calls `session.remove()` on every request, which closes and rolls back any uncommitted state. The early-return paths therefore discard their partial mutations rather than leaking them to the next request. Reporting a missing transaction boundary here would have been the family's most common false positive.
